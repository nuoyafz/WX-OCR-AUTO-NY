## 任务5：运行状态显示「错误」的诊断与修复
现象：启动后前3步(解析器/LLM/提取引擎)✔，但整体状态显示「● 错误」，日志无明确报错。
- 排查：engine 仅在 `initialize()` 返回 False 时调 `_on_status("error")`（main.py:421）；但 `initialize()` 全方法只有 `return True`、无 try/except、无 `return False`。真正原因：初始化或主循环的异常在守护线程 `_monitor_thread` 中**未被捕获→线程静默崩溃**，异常被吞掉，状态残留且无诊断。
- 修复：将 `_monitor_thread` 整体包 try/except，任意异常都打印完整堆栈并将状态正确置为 error（不再静默）。已 `git commit a622f93`。
- 待用户重启 ui_app.py 后复跑，日志会显示真实异常（含行号），据此定位具体失败步骤（最可能：步骤4数据存储/步骤5联系人监控·红点/步骤6 AI训练，或主循环首帧窗口相关）。

## 任务6：initialize() 结构被破坏导致启动即「错误」（7bc4e5e）
- 现象：日志停在第[3/6]步就报「错误」，无堆栈（上一轮的 try/except 没触发 = 不是异常路径）。
- 真因：之前插入 update_classification 方法时，把 initialize() 的步骤4(存储)/5(联系人+红点)/6(AI训练) 连同 return True 一起吞进了 update_classification 的方法体 → initialize() 无 return（返回 None）→ `if not self.initialize():` 为真 → 直接置 error。步骤4-6 永远不会执行。
- 修复：把步骤4-6+return True 还原回 initialize()；update_classification 恢复为独立小方法。改完 initialize() 实测跑通6步返回 True。
